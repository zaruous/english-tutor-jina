# 10.5 — 보안 강화 플랜 (2026-09-03)

2026-09-03 프로젝트 평가에서 나온 취약점을 기록하고, **플랜 11(관리자 콘텐츠 저작) 착수 전에** 닫는다.
번호가 10.5 인 이유: 플랜 11 이 `is_admin` 을 실제 권한으로 쓰기 시작하는 첫 플랜이라, 권한 경계와
서버측 요청 검증이 그보다 먼저 있어야 한다. 11 의 문서·번호는 건드리지 않는다.

## 0. 전제 — 지금까지의 보안 경계와 무엇이 바뀌나

지금까지 이 앱은 **"개발자 1인 PC 에서 돈다"** 를 전제로 설계됐다 (`pronunciation-sidecar.js` 머리말,
`auth.service.js` 의 인메모리 레이트리밋 주석). 그 전제에서는 아래 항목 대부분이 실제 위험이 아니다 —
사용자가 곧 서버 운영자이기 때문이다.

플랜 11 은 그 전제를 깬다. **관리자와 학습자가 같은 서버를 쓰는 다중 사용자 구조**가 되고, 학습자 계정으로
관리자 기능이나 서버 자원에 닿을 수 있으면 곧바로 사고다. 그래서 아래 취약점은 심각도를 두 열로 적는다:
**지금(1인)** 과 **11 이후(다중 사용자)**.

## 2. 설계 결정

1. **`requireAdmin` 을 `api/middleware/auth.js` 에 추가한다** — `requireUser` 위에 얇게 얹어 `user.is_admin` 이
   아니면 `403 FORBIDDEN`. 11 Phase 1 이 만들려던 것을 이 플랜으로 앞당긴다. 11 문서의 "권한" 행은 이 플랜을
   가리키도록 갱신한다(이 문서 범위 밖, 11 착수 시).
2. **사이드카 관리 3라우트는 `requireAdmin`** (S1). production 차단(`canManage`)은 그대로 둔다 — 두 조건은
   다른 걸 막는다(누가 vs 어디서).
   - 대가: dev 계정(`jina@dev.local`, `is_admin=false`)으로는 설정 화면의 [서버에 설치]/[시작] 버튼이 403 이 된다.
     개발 중에는 `admin/1234` 로 로그인하면 된다. `e2e-stt-settings.mjs` 는 admin 로그인으로 고쳐야 한다.
   - 대안(채택하지 않음): `is_dev OR is_admin` 허용. 편하지만 "dev 계정 = 반쪽 관리자" 라는 세 번째 권한 등급을
     만든다. 열린 질문 2.
3. **클라이언트 `ollamaUrl` 입력을 서버에서 받지 않는다** (S2). 5개 라우트에서 `ollamaUrl` 파싱을 지우고
   `askAI` 는 항상 `config.ai.ollamaUrl` 을 쓴다.
   - 대가: 설정 패널의 Ollama URL 입력(`src/main.jsx:378`)이 서버에 영향을 못 준다. 화면은 서버값을
     읽기 전용으로 표시하고, 바꾸려면 `.env` 의 `OLLAMA_URL`. `ai-provider.jsx:61` 의 브라우저 → Ollama
     `/api/tags` 직접 호출(교차 출처)도 같은 이유로 `GET /api/ai/providers` 의 서버 모델 목록으로 대체한다.
   - 대안(채택하지 않음): 호스트 allowlist(`localhost`/`127.0.0.1`). 루프백이어도 사이드카 :8000·API 자신에
     닿으므로 SSRF 가 남는다. 열린 질문 1.
4. **`GET /api/ai/health` 는 `requireUser`, `force=1` 은 `requireAdmin`** (S3). 캐시 읽기는 로그인 사용자
   누구나, 프로브 강제는 관리자만. 로그인 화면·오프라인 화면이 health 를 부르는지 확인하고 부른다면 그 호출을
   `/api/health`(무인증, DB 핑만)로 바꾼다.
5. **정적 서버는 `decodeURIComponent` → `path.normalize` → deny 검사 → `startsWith` 순서로** (S4).
   deny 정규식은 정규화된 경로에 건다. `Access-Control-Allow-Origin: *` 줄은 삭제한다(S5) — 정적 자원을
   교차 출처로 읽는 소비자가 없다(`canvas.html` 도 같은 출처).
6. **프록시가 `X-Forwarded-For` 를 붙이고, API 는 `remoteAddress === 127.0.0.1` 일 때만 그 헤더를 신뢰한다**
   (S6). `api/lib/client-ip.js` 한 함수로 뽑아 `auth.routes.js` 두 곳과 `middleware/auth.js` 가 같이 쓴다.
   레이트리밋을 인메모리에서 꺼내는 것(Redis 등)은 범위 밖 — 단일 프로세스 전제는 이 플랜이 바꾸지 않는다.
7. **S7 은 완화만 한다(Phase 3, 선택)** — `askAI` 진입 전에 사용자당 동기 요청 1건 세마포어. 근본 해결은
   동기 경로를 `ai_jobs` 로 옮기는 것이고 플랜 07 메모에 이미 있다. 이 플랜에서 30분 타임아웃 값은 건드리지 않는다
   (2026-08-31 사용자 결정).
8. **기본값(`DEV_AUTOLOGIN=1`, `admin/1234`)은 바꾸지 않는다.** E2E 스크립트 전부가 autologin 에 의존하고,
   관리자 기본 비밀번호는 방금(0016) 사용자가 정한 것이다. 열린 질문 3 으로 남긴다.

## 4. 검증 — `scripts/verify-security.mjs` (신규, AI provider 불필요)

`npm run dev` 가 떠 있는 상태에서 실행. 기대값은 상태 코드와 부작용 0 으로 단정한다.
표의 라인 번호가 아니라 **행동**을 검증한다.

| 대상 | 절차 | 기대 |
|---|---|---|
| S1 | dev 계정(autologin 쿠키)으로 `POST /api/speaking/sidecar/start` | 403 `FORBIDDEN`, `lib/pronounce/.sidecar.pid` 미생성 |
| S1 | admin 로그인 쿠키로 같은 요청 | 미설치면 409 `CONFLICT`(설치 안 됨) — 권한은 통과했다는 증거. 설치 상태면 200 후 `stop` 으로 정리 |
| S2 | 로컬 HTTP 리스너(임의 포트) 띄우고 `POST /api/ai/chat { provider:'ollama', ollamaUrl:'http://127.0.0.1:<port>' }` | 리스너 히트 0건. 응답은 서버 `OLLAMA_URL` 기준 결과(Ollama 미기동이면 503) |
| S3 | 쿠키 없이 `GET /api/ai/health?force=1` (`X-Jina-No-Autologin: 1`) | 401 |

## 5. 구현자 메모

- `requireAdmin` 은 `optionalUser` 를 우회하지 않는다 — `DEV_AUTOLOGIN` 세션 발급은 그대로 일어나고
  그 뒤에 `is_admin` 만 본다. 캔버스(`X-Jina-Mode: canvas`)의 non-GET 403 은 `api/server.js` 에서 먼저 걸리므로 순서 무관.
- `ollamaUrl` 제거 시 `askAI` 호출부는 5개 라우트 + `ai-job-worker.js` — 워커는 원래 안 넘기니 무변경. `registry.js`
  의 `providerHealth({ ollamaUrl })` 인자도 함께 지운다(호출부 확인).
- `server.js` 의 `startsWith(__dirname)` 검사는 정규화 후에도 유지 — deny 정규식과 역할이 다르다(루트 이탈 vs 민감 경로).
- `X-Forwarded-For` 는 프록시가 **덮어쓴다**(클라이언트가 보낸 값을 이어붙이지 않는다). 정적 서버 앞에 다른
  리버스 프록시를 두는 배포는 이 플랜 범위 밖이고, 그때는 `clientIp` 의 신뢰 조건을 바꿔야 한다.
- 이 플랜은 마이그레이션 0건. `is_admin`(0016) 그대로 쓴다.

## 6. 열린 질문

1. **Ollama URL 기기별 설정을 포기하는가** — 결정 3 의 대가. 남기려면 서버측 allowlist 인데 루프백 SSRF 는 남는다.
2. **사이드카 버튼을 dev 계정에도 열어둘지** — `is_dev OR is_admin`. 편의 vs 권한 등급 하나 추가.
