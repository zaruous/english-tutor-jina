# 10.7 — DB 기반 재정비 (2026-09-03)

2026-09-03 평가 대화에서 나온 세 가지 결정을 하나로 묶는다: **테스트를 쉽게** 만들고, **DB 를 새로**
잡고, 그 기회에 **콘텐츠 테이블을 통합**한다. 플랜 11~13(관리자 콘텐츠)의 선행 플랜이다.

> **전제 (사용자 확인, 2026-09-03)**: 현재는 구현 단계이고 **기존 DB 를 드롭·재생성해도 문제없다.**
> 그래서 이 플랜은 데이터 이동 마이그레이션을 쓰지 않는다 — 새 baseline 을 만들고 시드를 다시 넣는다.
> 이 전제가 깨지면(보존할 데이터가 생기면) Phase 2 는 전면 재작성해야 한다.

## 0. 왜 지금인가

| 지금 문제 | 이 플랜이 바꾸는 것 |
|---|---|
| 단위 테스트 0 · 린트 0 · CI 0. 검증 스크립트 전부가 **서버 + PostgreSQL + 실 AI provider** 를 요구 | `DB_DRIVER=pglite` 로 DB 설치 없이 서비스 계층을 테스트. CI 에서 돌아간다 |
| 콘텐츠가 3테이블에 나뉘어 가시성 조건이 **27곳**, `published` 가 **20곳** | `content_items` 한 테이블로 통합 → 조건이 조인 한 곳 |
| `topic_contents` 배타 FK + 부분 UNIQUE 3개, 타입 추가마다 제약 교체 | `(topic_id, content_id)` 단일 FK. 13 의 `0018` 이 detail 테이블 하나로 축소 |
| 콘텐츠 시드가 체크섬 불변 마이그레이션 안에 ~300줄 → 관리자가 편집하면 `db:reset` 이 지운다 | `db/content/*.json` + import 스크립트. 마이그레이션은 스키마만 |
| `public` 스키마를 다른 앱과 공유 → `RESET_TABLES` 23개 수기 목록 + `FOREIGN_TABLES` self-assert | 전용 DB `jina_eng` + 스키마 `app` → `DROP SCHEMA app CASCADE`. 남의 테이블이 없으니 목록·self-assert 는 **존재 이유가 사라진다** |
| 마이그레이션 16개 누적, 0015 는 0005 의 CHECK 를 교체하는 등 층이 겹침 | `0001_baseline.sql` 하나 |

**Phase 1 을 먼저 두는 이유**: 하네스를 기존 스키마 위에서 먼저 만들면 하네스 자체가 검증되고,
그다음 위험한 재설계(Phase 2)에 **안전망이 생긴다.** 순서를 뒤집으면 "테스트가 없는 상태에서 145개
쿼리를 다시 쓰는" 일이 된다.

## 1. SQLite 를 채택하지 않는다 — 실측 근거

SQLite 병행 지원은 목표("구현·테스트 용이")에는 맞지만 수단이 틀렸다. 이 코드베이스는 집계·파생값을
SQL 안에서 계산하는 것이 설계 원칙(DTO 서버 단일 소스)이고, 그 SQL 이 PostgreSQL 전용 기능에 깊이 의존한다.

`api/` + `db/` 실측 (2026-09-03):

| 구문 | 횟수 | SQLite 에서 |
|---|---|---|
| `::jsonb` · `jsonb_*()` | 83 | JSON1 함수로 전부 재작성 |
| `AT TIME ZONE` · `::date` · `date_trunc` · `::interval` | 81 | **타임존 함수 없음** — `APP_TZ` 일자 경계를 앱에서 계산 |
| `FILTER (WHERE …)` · `LATERAL` | 42 | LATERAL 없음 |
| `ON CONFLICT DO UPDATE` · `RETURNING` | 58 | 3.35+ 한정 |
| `pg_advisory_xact_lock` · `to_regclass` · `generate_series` · `DISTINCT ON` | 20 | 대응 없음 |
| `.query()` 호출부 | 145 | 전부 두 방언 |

세 가지가 치명적이다.
1. **테스트가 다른 엔진을 검증한다.** SQLite 에서 통과한 대시보드 집계가 PostgreSQL 에서 타임존 경계
   하나로 어긋난다. 회귀를 잡으려는 테스트가, 회귀가 가장 잘 나는 지점에서 눈을 감는다.
2. **추상화 계층이 강제된다.** 145 호출을 두 번 쓰지 않으려면 쿼리 빌더/ORM 이 필요하고, 그 순간
   "SQL 이 단일 소스" 규범이 깨진다. API 6.6k LOC 의 절반이 다시 쓰인다.
3. **영구 세금이다.** 이후 모든 쿼리가 두 방언에서 검증되어야 한다. 1인 개발에서 기능마다 반복된다.

동시성 모델도 다르다 — `ai_jobs` 중복 방지가 advisory lock 에, 워커·세마포어가 커넥션 풀에 의존한다.

## 2. 대안 — 같은 엔진, 두 드라이버 (실측 검증됨)

방언을 늘리지 말고 **실행 방식**만 둘로 둔다. `.env`:

```
DB_DRIVER=pg          # 기본. 실 PostgreSQL (PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD)
DB_DRIVER=pglite      # 개발·테스트. WASM PostgreSQL, 설치 불필요
PGLITE_DATA_DIR=      # 비우면 메모리(테스트마다 새 DB), 경로를 주면 파일 영속
PGDATABASE=jina_eng   # 전용 데이터베이스 (사용자 확정 2026-09-03) — 옛 `jina` 는 더 이상 열지 않는다
DB_SCHEMA=app         # 전용 스키마 (Phase 2)
```

[PGlite](https://www.npmjs.com/package/@electric-sql/pglite) 는 PostgreSQL **자체**를 WASM 으로 컴파일한
것이라 SQL 을 한 줄도 바꾸지 않는다. 대체 경계는 `api/lib/pool.js` **한 파일**이고 145개 호출부는 무변경이다.

### 2.1 실측 결과 (`@electric-sql/pglite@0.5.8`, 2026-09-03)

`PGlite.create()` → `SHOW server_version` = **18.3** (진짜 Postgres). 이 프로젝트가 쓰는 구문을 직접 실행:

| 검증 항목 | 결과 |
|---|---|
| `BIGSERIAL` · `TIMESTAMPTZ` · `CHECK(num_nonnulls…)` · 정규식 CHECK(`~`) | OK |
| `ON CONFLICT … DO UPDATE … RETURNING` | OK |
| `jsonb_typeof` · `jsonb_array_length` · `jsonb_each_text`(오답 노트 쿼리) | OK |
| `AT TIME ZONE 'Asia/Seoul'` · `::date` · `date_trunc` · `::interval` | OK |
| `generate_series`(주간 7칸) · `FILTER (WHERE)` · `DISTINCT ON` · `LATERAL` | OK |
| `to_regclass`(테이블 부재 폴백) · 부분 UNIQUE 인덱스 · CTE + 윈도우 함수 · `DO $$` | OK |
| `transaction()` + `pg_advisory_xact_lock(hashtext($1))` | OK |
| `SET statement_timeout` | OK |
| 파일 영속 → 프로세스 재시작 후 재오픈 | OK |
| `COMMENT ON TABLE/COLUMN` + `obj_description()` (§3.4 규약) | PGlite **미실측** — 실서버 16.15 에서는 OK(23건) |
| `CREATE FUNCTION … LANGUAGE plpgsql` + `BEFORE UPDATE` 트리거(§3.4 `set_updated_at`) | PGlite **미실측** — 실서버 16.15 에서 생성·발화 모두 OK. `DO $$` 는 PGlite 에서 이미 통과했으므로 plpgsql 자체는 있다 |

> **실서버 버전이 확인됐다 — PostgreSQL 16.15** (2026-09-03, `jina_eng` 접속). PGlite 는 18 이므로
> §2.2 의 버전 스큐가 **실재한다**(2 메이저 차이). CI 는 `pglite` 로 빠르게, 릴리스 전 1회는 `pg` 로.

**어댑터가 반드시 처리할 차이 1건 (실측):** `pool.js` 는 `pg.types.setTypeParser(20, Number)`(BIGINT)와
`(1700, Number)`(NUMERIC)로 문자열 반환을 막는다. PGlite 는 BIGINT 는 `number` 로 주지만
**NUMERIC 은 `"2.50"` 문자열로 준다.** 그대로 두면 `pool.js` 주석이 경고한 "프론트 비교·산술이 조용히
깨지는" 상황이 재현된다. PGlite 는 쿼리 옵션으로 파서를 받으므로 어댑터가 항상 주입한다:

```js
await db.query(sql, params, { parsers: { 1700: Number } })   // 실측 확인: 2.5 (number)
```

### 2.2 PGlite 의 한계 — 무엇을 못 잡는가

- **단일 커넥션이다.** `PG_POOL_MAX` 는 의미가 없고 트랜잭션이 직렬화된다. advisory lock 은 동작하지만
  **경합이 없어 동시성 버그를 잡지 못한다.** `ai_jobs` 중복 방지·워커 경합·세마포어는 `DB_DRIVER=pg` 로
  검증해야 한다(기존 `verify-lesson-gen.mjs` 의 역할).
- **버전 스큐.** PGlite 는 PostgreSQL 18 이고 실 서버 버전은 환경마다 다르다. 18 에서 통과한 문법이
  구버전에서 거부될 수 있다 → CI 는 `pglite` 로 빠르게, 릴리스 전 1회는 `pg` 로 전체 회귀(Phase 3).
- **0.x 이다.** 2026-08-26 릴리스, 활발하지만 pre-1.0 이라 API 파괴 변경 가능 → **정확한 버전 고정**.
- **Node 버전 미확인.** 패키지에 `engines` 필드가 없고, 실측은 Node 22 에서 했다. `package.json` 은
  `>=18` 이다 — Node 18 에서 PGlite 와 `node:test` 를 확인하고, 안 되면 `engines` 를 `>=20` 으로 올린다
  (열린 질문 2).

## 3. 스키마 재설계

### 3.1 전용 데이터베이스 + 전용 스키마

> **사용자 확정 (2026-09-03)**: 새 데이터베이스 **`jina_eng`** 을 만들고 스키마를 재구성한다.
> 옛 DB `jina` 는 그대로 두고 **더 이상 열지 않는다** — 드롭조차 하지 않는다.

이 결정이 제약 하나를 통째로 없앤다. 지금까지 `db/migrate.mjs` 는 같은 스키마에 사는 **다른 앱 테이블 11개**를
건드리지 않으려고 `RESET_TABLES` 23개 수기 목록과 `FOREIGN_TABLES` self-assert 를 유지해 왔다.
전용 DB 에는 **남의 테이블이 아예 없으므로** 그 방어 장치가 대체되는 게 아니라 **존재 이유가 사라진다.**
테이블을 추가할 때마다 목록을 FK 역순으로 갱신하던 부담(플랜 11·13 이 반복해서 적던 것)도 같이 끝난다.

전용 DB 안에서 **다시 전용 스키마 `app`(`DB_SCHEMA`)** 을 쓴다. DB 가 우리 것뿐이라 `public` 을 써도 되지만:

- `db:reset` 이 `DROP SCHEMA app CASCADE; CREATE SCHEMA app;` 두 줄로 끝난다. `public` 을 드롭·재생성하는
  경로는 PostgreSQL 15 부터 기본 ACL 이 달라져(`PUBLIC` 의 CREATE 회수) 재생성 후 GRANT 를 다시 봐야 한다.
  앱 롤이 소유한 별도 스키마는 그 함정을 비껴간다.
- 이 프로젝트는 `CREATE EXTENSION` 을 하나도 쓰지 않는다(실측 — `gen_random_uuid()` 는 PG13+ 코어).
  그래서 `public` 에 남겨 둘 것이 없고, `app` 을 통째로 날려도 잃는 것이 없다.
- 최소권한 롤 분리(`db/README` 후속 과제)의 GRANT 범위가 스키마 하나로 떨어진다.

쿼리의 `public.` 접두 145곳은 `search_path` 를 스키마로 고정하고 **접두를 제거**한다(어댑터가 두 드라이버
모두에 `SET search_path` 를 건다). 접두를 `app.` 으로 바꾸는 것보다 낫다 — 스키마 이름이 코드에 박히지 않는다.

### 3.2 콘텐츠 카탈로그 통합

```
content_items                         -- 콘텐츠 공통 상위. 가시성·감사·토픽 구성이 전부 여기만 본다
  id, type (lesson|scenario|vocab_set|speaking_set),
  slug UNIQUE, title, description, difficulty,
  status (draft|review|published|archived), visibility (public|private),
  source (seed|ai|curated), created_by, updated_by, created_at, updated_at
  CHECK (status IN ('published','archived') OR visibility = 'private')   -- 11 결정 1 · 열린 질문 7 → 후보 A 확정

lesson_details      (content_id PK → content_items)  kind, subtitle, est_minutes, passage, vocab, faq, position
scenario_details    (content_id PK)                  tag, level, system_prompt, opening_message, objectives
vocab_set_details   (content_id PK)                  words
-- speaking_set_details 는 13 Phase C (플랜 10 실측 통과 후)

lesson_items.content_id            → content_items    (lesson_id 개명)
user_lesson_attempts.content_id    → content_items    (lesson_id 개명)
lesson_drafts.published_content_id → content_items    (published_lesson_id 개명 — 이 컬럼의
   'published' 는 "이 초안에서 발행된 레슨" 이라는 뜻이고, 폐지되는 lessons.published 불리언과 무관하다)
   -- review_status 는 baseline 에 없다(11 결정 8). 승인 상태의 단일 소스는 content_items.status 이고,
   --   레슨에만 있는 이 컬럼을 살리면 시나리오·단어 세트는 반려를 기록할 자리가 없다.
   --   lesson_drafts 는 생성 산출물·validation_errors 보관용으로만 남는다.
topic_contents (topic_id, content_id, position)  UNIQUE (topic_id, content_id)
   -- 배타 FK · 부분 UNIQUE 3개 · num_nonnulls CHECK 전부 소멸
content_audit_log.content_id       → content_items    (다형성 아닌 진짜 FK)
topics: status·visibility·updated_by 를 baseline 에 포함
```

**CHECK 형태는 확정됐다 (11 열린 질문 7 → 후보 A).** 처음 초안은 `status = 'published' OR visibility = 'private'`
이었는데, 그러면 `archived` 행이 강제로 `private` 이 되어 11 결정 2 의 `resolvable`(내린 콘텐츠가 오답 노트·통계에는
남는다)이 무력화된다 — 시드 레슨을 푼 학습자는 그 레슨의 작성자가 아니므로 `created_by` 가지로도 못 걸린다.
`status IN ('published','archived')` 로 좁히면 draft·review 의 오발행 방지는 그대로 두면서 archived 가
**이전 가시성을 보존**하고, 내렸다 다시 올리는 왕복도 성립한다.

이 통합으로 플랜 11 이 예정했던 것들이 **불필요해진다**: `0017_content_status.sql`,
`lessons.published` 정합성 CHECK(컬럼 자체가 없다), 네 테이블에 `status` 개별 추가, 13 의 배타 FK 확장.

**같은 김에 고치는 것 하나 — LC 스크립트 구조화.** 지금 `passage.body` 는 `"W: Do you have…"` 문자열
배열이고, 재생은 정규식으로 화자 라벨을 떼고 `validateLcScript` 도 문자열을 파싱한다. 13 의 에디터가
줄 단위로 편집할 대상이므로 `[{speaker: 'W'|'M', text}]` 로 바꾼다. 영향: `listening.jsx`,
`speaking.service.js`(문장 은행), `validateLcScript`, `lesson_gen` LC 스키마·프롬프트.

### 3.3 권한 — `users.is_admin` → `users.role`

승인 워크플로(11~13)는 "만드는 사람"과 "그것을 승인하는 사람"을 구분해야 하는데 `is_admin` 불리언으로는
못 한다. 게다가 같은 플래그가 10.5 가 지키는 **시스템 조작**(사이드카 설치·프로세스 스폰)까지 겸하고 있어,
위험도가 다른 둘을 한 열쇠로 연다. baseline 을 새로 잡는 김에 축을 하나 세운다.

`users.role` 은 `roles(code)` 를 참조하고, 등급 정의·서열·설명이 그 테이블에 산다(DDL 은 §3.4).
`is_admin` 불리언은 baseline 에 없다. 0016 의 `ADMIN_*` 부팅 동기화는 `role='admin'` 으로 넣는다.

계정을 막는 수단은 공통 컬럼 `users.is_active` 가 담당한다(11 열린 질문 8 → 해소). Phase 3 사용자 관리에
문제 계정을 막을 방법이 하나도 없었는데 — 삭제는 `ON DELETE CASCADE` 로 학습 이력까지 지우고, 세션 종료는
재로그인하면 그만이다 — `resolveSession` 의 WHERE 에 `u.is_active AND NOT u.is_deleted` 한 줄이면
`role` 과 **같은 경로로 매 요청 최신값을 읽으므로** 즉시 차단되고 별도 무효화가 필요 없다.
언제 누가 껐는지는 `user_audit_log(action='disable')` 이 갖는다 — 컬럼에 시각을 또 두지 않는 이유다.

**서열이다** — `learner < author < reviewer < admin`. 다대다 `user_roles` 테이블을 만들지 않는 이유는
이 앱의 권한 질문이 전부 "이 이상인가?" 한 가지이기 때문이다. 검사도 `rank(user.role) >= rank(required)`
한 줄이고, 1인 운영에서 admin 하나면 지금과 똑같이 동작한다. 역할이 실제로 갈라질 때 열 하나만 바꾸면 된다.
누가 무엇을 할 수 있는지의 표는 [11 결정 6](11-content-lifecycle-admin.md#2-설계-결정).

시드도 이 축을 쓴다 — 개발 계정 `jina@dev.local` 에 `role='admin'` 을 주면 **10.5 열린 질문 2**
(사이드카 버튼을 dev 계정에도 열지)가 `is_dev OR is_admin` 같은 세 번째 권한 등급 없이 풀린다.

**역할 변경은 세션 무효화가 필요 없다.** `resolveSession`(`auth.service.js:80`)이 요청마다
`auth_sessions JOIN users` 로 사용자 행을 다시 읽으므로 `role` 은 항상 최신이고, 강등이 **다음 요청부터**
곧바로 적용된다. 세션에 권한을 실어 두는 구조였다면 무효화 경로가 필요했을 것이다 — 이 성질을 깨지 않도록
`role` 을 세션 토큰이나 JWT 류에 넣지 않는다.

역할 변경 이력은 `content_audit_log` 에 넣을 수 없다 — 그 테이블의 `content_id` 는 `content_items` 를 향한
**진짜 FK** 이고(§3.2), 사용자를 가리키려면 다형성으로 되돌아가야 한다. 그래서 작은 테이블을 하나 더 둔다:

작은 테이블 `user_audit_log` 를 하나 더 둔다(DDL 은 §3.4) — 역할 변경·세션 종료·사용 중지를 남기고,
행위자와 대상이 **둘 다 `users(id)` 를 향한 진짜 FK** 다. 하나로 합치면 대상 컬럼이 nullable 두 개가 되어
§3.2 에서 없앤 다형성이 감사 테이블로 옮겨올 뿐이다.

**범위에 넣지 않는 것 — 자유로워졌다고 넓히지 않는다.** 전용 DB 로 풀린 제약은 "데이터를 보존해야 한다" 였지
"규모가 크다" 가 아니다. 근거가 그대로인 항목은 그대로 둔다:

- `user_lesson_attempts.answers` JSONB → 문항 단위 행 정규화. 사용자당 수백 건 규모에서 이득이 없다
  (08 구현자 메모의 판단 유지). 이 플랜의 목표는 성능이 아니라 구조다.
- `daily_progress` 적재(03 follow_up) · 최소권한 롤 분리(`db/README`) — 별개 문제이고 baseline 과 무관하다.
- 테이블 이름 일괄 개명 — 컬럼(`lesson_id → content_id`)은 FK 대상이 바뀌어 의미가 어긋나므로 고치지만,
  테이블 이름은 어긋나지 않는다. 개명 자체가 목적이 되면 145곳 쿼리를 이유 없이 다시 읽어야 한다.

#### 공통 컬럼 규약 (2026-09-03 사용자 지시)

모든 테이블이 **고유 컬럼 + 아래 공통 세트**로만 이루어진다. 테이블마다 다르게 쓰지 않는 것이 이 규약의 요점이다.

```sql
-- ▼ 공통 컬럼 세트 (COMMON) — 아래 DDL 에서 `[COMMON]` 으로 줄여 쓴다. baseline 에서는 펼쳐 쓴다.
  description TEXT        NOT NULL DEFAULT '',        -- 행 설명(데이터). 테이블 설명은 COMMENT ON.
  is_active   BOOLEAN     NOT NULL DEFAULT true,      -- 사용 여부. false = 보존하되 쓰지 않음
  is_deleted  BOOLEAN     NOT NULL DEFAULT false,     -- 삭제 여부(soft delete). 물리 삭제는 하지 않는다
  deleted_at  TIMESTAMPTZ,
  deleted_by  BIGINT      REFERENCES users(id) ON DELETE SET NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  created_by  BIGINT      REFERENCES users(id) ON DELETE SET NULL,
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_by  BIGINT      REFERENCES users(id) ON DELETE SET NULL,
  cmf_1 TEXT, cmf_2 TEXT, cmf_3 TEXT, cmf_4 TEXT, cmf_5  TEXT,
  cmf_6 TEXT, cmf_7 TEXT, cmf_8 TEXT, cmf_9 TEXT, cmf_10 TEXT,
  CONSTRAINT <tbl>_del_ck CHECK (is_deleted = (deleted_at IS NOT NULL))   -- 플래그와 시각이 어긋나지 않게
```

`updated_at` 은 앱이 아니라 트리거가 채운다 — 145곳 쿼리에 `updated_at = now()` 를 흩뿌리지 않기 위해서다.

```sql
CREATE FUNCTION set_updated_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN NEW.updated_at = now(); RETURN NEW; END $$;
-- 각 테이블: CREATE TRIGGER trg_<tbl>_updated BEFORE UPDATE ON <tbl>
--              FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

지켜야 할 것 네 가지:

1. **`cmf_1` ~ `cmf_10` 은 쓰기 시작할 때 `COMMENT ON COLUMN` 을 단다.** 그러지 않으면 반년 뒤 `cmf_3` 이
   무엇인지 아무도 모른다. 슬롯이 자리를 잡으면(쿼리 조건이나 인덱스가 붙으면) 이름 있는 컬럼으로 승격한다.
2. **`COMMENT ON` 은 테이블 전부와 자명하지 않은 컬럼에 단다.** `\d+`·`obj_description()` 으로 읽히므로
   스키마 자체가 문서가 된다. 역할 설명·전이 메뉴 라벨은 한 걸음 더 나가 **테이블 데이터**로 둔다(아래).
3. **soft delete 는 UNIQUE 를 부분 인덱스로 바꾼다.** `is_deleted` 행이 이메일·slug 를 계속 붙들고 있으면
   같은 값으로 다시 만들 수 없다. `UNIQUE (email)` 대신 `CREATE UNIQUE INDEX … WHERE NOT is_deleted`.
4. **조회 조건에 `is_deleted`·`is_active` 가 들어간다.** `api/lib/content-scope.js` 의 `discoverable`·
   `resolvable` 이 이 둘을 함께 걸어야 하고(11 결정 2), 빠뜨리면 지운 콘텐츠가 화면에 남는다.

**append-only 로그는 예외다.** `content_audit_log`·`user_audit_log` 는 `created_at`·행위자만 갖고
`is_active`·`is_deleted`·`updated_*` 를 두지 않는다 — 수정·삭제되는 감사 기록은 감사 기록이 아니다.
`cmf_*` 와 `description` 은 로그에도 둔다(공통 규약 유지).

```sql
  self_review     BOOLEAN     NOT NULL DEFAULT false,
  description     TEXT        NOT NULL DEFAULT '',   -- 반려 사유 등 자유 기술
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  created_by      BIGINT      REFERENCES users(id) ON DELETE SET NULL,   -- 행위자
  cmf_1 TEXT, … cmf_10 TEXT,
  CONSTRAINT content_audit_action_ck
    CHECK (action IN ('create','update','status_change','visibility_change','delete'))

CREATE INDEX content_audit_target_idx ON content_audit_log (content_id, created_at DESC);

COMMENT ON TABLE  content_audit_log             IS 'append-only. 상태·가시성 전이와 저작 행위를 남긴다. 수정·삭제 컬럼을 두지 않는다 — 고쳐지는 감사 기록은 감사 기록이 아니다.';
COMMENT ON COLUMN content_audit_log.created_by  IS '행위자. ON DELETE SET NULL — 계정을 지워도 기록은 남는다.';

```

**닭과 달걀 하나**: `[COMMON]` 의 `created_by`·`updated_by`·`deleted_by` 가 `users(id)` 를 참조하는데
`roles` 가 `users` 보다 먼저 만들어져야 한다(`users.role` FK). baseline 은 ① 모든 테이블을 FK 없이 생성 →
② `ALTER TABLE … ADD CONSTRAINT` 로 FK 일괄 추가 순으로 쓰거나, `roles`·`content_statuses` 의 감사 FK 만
나중에 붙인다. 한 파일이므로 순서만 정하면 되는 문제다.

**이 설계가 코드에서 없애는 것**: 역할 서열 하드코딩(`roles.rank` 조회로 대체), 전이 허용 목록 하드코딩
(`content_transitions` 조회로 대체), 화면 문구 하드코딩(역할 설명·전이 라벨이 데이터). `canTransition(from,to,role)`
은 두 테이블을 조인한 한 번의 조회가 되고, 관리 화면의 `[▾]` 메뉴는 **현재 상태와 내 역할로 뽑은 전이 목록**을
그대로 그린다 — 화면과 서버가 같은 표를 본다.

**대가**: 규칙이 데이터라 마이그레이션 없이 바뀔 수 있다. `content_transitions` 는 시드로 관리하고
(`db/content/` 가 아니라 baseline 안에 둔다) 변경은 코드 리뷰를 거치게 한다.

### 3.5 기준정보 (공통 코드) — `code_groups` · `codes`

파일: [`db/baseline/0002_common_codes.sql`](../../db/baseline/0002_common_codes.sql) (적용 완료, 29ms).

**왜 필요한가 — 실측으로 확인된 이중 소스.** 열거값이 지금 두 곳에 갈라져 있다.

| 값 | 허용값이 있는 곳 | 라벨·색이 있는 곳 |
|---|---|---|
| `skill_code` 5종 | `lesson_items_skill_ck`(0012) | `src/screens/mistakes.jsx:9` `SKILL_LABELS` |
| 첨삭 유형 3종 | `corrections_type_ck`(0004) | `src/screens/conversation-desktop.jsx:152` `CORRECTION_TYPE_META` |
| 레슨 종류 3종 | `lessons_kind_ck`(0015) | 화면마다 산재 |

`mistakes.jsx:9` 의 주석이 **"값은 `lesson_items_skill_ck` 가 허용하는 5종"** 이라고 적어 둔 것이
두 곳을 사람이 손으로 맞추고 있다는 증거다. 코드를 하나 늘리면 마이그레이션과 JSX 를 같이 고쳐야 한다.

**경계 — 무엇을 여기 두고 무엇을 두지 않는가.** 이 구분이 이 절의 핵심이다.

- **전용 테이블로 남긴다** — 다른 테이블이 FK 로 참조하거나(`roles`, `content_statuses`),
  값에 **동작이 딸린** 것(`roles.rank` 서열 비교, `content_transitions` 전이 규칙).
- **`codes` 로 온다** — 화면 라벨·필터 칩·드롭다운. 코드가 늘어도 로직이 안 바뀌는 긴 꼬리.

**앞선 판단을 정정한다.** 이 문서 이전 개정에서 "범용 코드 테이블은 FK 를 못 걸어서 후퇴" 라고 적었는데
**틀렸다.** 소비 컬럼 옆에 그룹을 고정한 생성 컬럼을 두면 복합 FK 가 걸린다 —
PostgreSQL 16.15 에서 실측했다:

```sql
ALTER TABLE app.lesson_items
  ADD COLUMN skill_group TEXT GENERATED ALWAYS AS ('SKILL_CODE') STORED,
  ADD CONSTRAINT lesson_items_skill_fk
    FOREIGN KEY (skill_group, skill_code) REFERENCES app.codes(group_code, code);
```

실측 결과: 유효 코드 통과 · **다른 그룹의 코드 거부**(`spelling` 을 `skill_code` 에 못 넣는다) ·
없는 코드 거부 · `NULL` 허용(MATCH SIMPLE) · 참조 중인 코드는 물리 삭제 거부.
다만 **`is_active = false` 는 FK 가 막지 않는다** — 사용 중지된 코드를 새로 쓰는 것은 앱이 걸러야 한다.

그래도 `roles`·`content_statuses` 를 옮기지는 않는다. 이유가 FK 에서 **동작**으로 바뀔 뿐이다:
`rank` 비교와 전이 규칙이 그 테이블에 딸려 있어서, 옮기면 `codes` 에 그 컬럼들이 따라와 그룹마다
쓰이지 않는 컬럼이 생긴다. Phase 2 에서 `lesson_items.skill_code` 등을 이관할 때 위 패턴을 쓴다.

**설계 세부 둘.** ① `codes` 의 PK 는 `(group_code, code)` 이고 **부분 UNIQUE 를 걸지 않는다** —
다른 테이블과 반대로 간 것이다. 지운 코드의 값을 재사용하지 못하는 것이 의도다. 과거 이력이 그 문자열을
가리키고 있어서 같은 코드에 다른 뜻을 붙이면 지난 데이터의 의미가 조용히 바뀐다.
② `cmf_*` 슬롯의 뜻은 그룹마다 다를 수 있으므로 `COMMENT ON COLUMN` 으로 적을 수 없다.
그래서 **`code_groups.description` 에 적는다** — 슬롯 의미가 스키마가 아니라 데이터에 산다.

## 6. 구현자 메모

- `db.js` 는 `query`/`tx` 두 함수만 노출한다. `pool.on('error')`(원격 유휴 커넥션 단절로 서버가 죽는 것을
  막는 기존 방어)는 pg 드라이버 쪽에 그대로 유지 — pglite 에는 해당 사항이 없다.
- 어댑터에서 `SET statement_timeout` 은 세션 단위다. 지금은 pg 연결 문자열의 `options` 로 넣고 있는데,
  pglite 는 그 경로가 없으므로 두 드라이버 모두 부팅 시 세션 설정으로 통일한다.
- `to_regclass` 폴백(01/02 테이블 부재 DB 에서도 대시보드 200)은 baseline 이후 무의미해진다 — 한 파일이
  전부를 만든다. 제거 여부는 Phase 2 에서 판단(제거하면 `dashboard.service` 가 눈에 띄게 단순해진다).
- 시드 JSON 은 스키마를 갖는다(`db/content/README.md`). 관리자 저작(13)이 들어오면 이 포맷이 export
  대상이 되므로 처음부터 DTO 와 가깝게 만든다.
- 마이그레이션 파일을 지우는 것은 이 프로젝트 규범("적용된 파일 수정 금지")의 **예외**다. 전제(드롭 가능)가
  근거이고, 같은 예외를 다시 쓰려면 이 문서를 갱신해야 한다.
- PGlite 데이터 디렉터리(`PGLITE_DATA_DIR`)를 `.gitignore` 에 추가한다.

3. **`DB_DRIVER=pglite` 를 개발 기본값으로 둘지** — DB 설치 없이 `npm run dev` 가 뜨는 것은 매력적이지만,
   개발자가 실 PostgreSQL 과 다른 환경에서 계속 작업하게 된다. 테스트 전용으로 두는 편이 안전해 보인다.
4. ~~**`lesson_items`·`user_lesson_attempts` 의 컬럼명**~~ → **`content_id` 로 통일**. 데이터 이동이 없는
   baseline 이라 개명 비용이 0 이고, FK 대상이 `content_items` 인데 컬럼만 `lesson_id` 로 남으면 조인을 읽을 때마다
   "이게 레슨만 가리키나?" 를 되묻게 된다. 테이블 이름(`user_lesson_attempts`)은 그대로 둔다 — 실제로 레슨
   시도만 기록하고, 스피킹 채점 이력이 생기면 그때 별도 테이블이다(13 결정 4).
5. **`type` 별 detail 테이블 vs `content_items.detail JSONB`** — detail 3~4개 테이블이 조인을 늘린다.
   JSONB 한 컬럼이면 조인이 없지만 CHECK 로 지키던 구조 검증을 잃는다. 전자를 제안(현재 스키마가 이미
   `passage`·`options` 를 JSONB 로 두고 나머지는 컬럼으로 둔 절충과 같은 결).
