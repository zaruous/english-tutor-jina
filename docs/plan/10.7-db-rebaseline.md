# 10.7 — DB 기반 재정비 (2026-09-03)

2026-09-03 평가 대화에서 나온 세 가지 결정을 하나로 묶는다: **테스트를 쉽게** 만들고, **DB 를 새로**
잡고, 그 기회에 **콘텐츠 테이블을 통합**한다. 플랜 11~13(관리자 콘텐츠)의 선행 플랜이다.

> **전제 (사용자 확인, 2026-09-03)**: 현재는 구현 단계이고 **기존 DB 를 드롭·재생성해도 문제없다.**
> 그래서 이 플랜은 데이터 이동 마이그레이션을 쓰지 않는다 — 새 baseline 을 만들고 시드를 다시 넣는다.
> 이 전제가 깨지면(보존할 데이터가 생기면) Phase 2 는 전면 재작성해야 한다.

## 0. 왜 지금인가

| 지금 문제 | 이 플랜이 바꾸는 것 |
|---|---|
| 단위 테스트 0 · 린트 0 · CI 0. 검증 스크립트 전부가 **서버 + PostgreSQL + 실 AI provider** 를 요구 | `DB_DRIVER=pglite` 로 DB 설치 없이 서비스 계층을 테스트. CI 에서 돌아간다 |
| 콘텐츠가 3테이블에 나뉘어 가시성 조건이 **27곳**, `published` 가 **20곳** | `content_items` 한 테이블로 통합 → 조건이 조인 한 곳 |
| `topic_contents` 배타 FK + 부분 UNIQUE 3개, 타입 추가마다 제약 교체 | `(topic_id, content_id)` 단일 FK. 13 의 `0018` 이 detail 테이블 하나로 축소 |
| 콘텐츠 시드가 체크섬 불변 마이그레이션 안에 ~300줄 → 관리자가 편집하면 `db:reset` 이 지운다 | `db/content/*.json` + import 스크립트. 마이그레이션은 스키마만 |
| `public` 스키마를 다른 앱과 공유 → `RESET_TABLES` 22개 수기 목록 + `FOREIGN_TABLES` self-assert | 전용 스키마 → `DROP SCHEMA jina CASCADE` 한 줄. 목록·self-assert 소멸 |
| 마이그레이션 16개 누적, 0015 는 0005 의 CHECK 를 교체하는 등 층이 겹침 | `0001_baseline.sql` 하나 |

**Phase 1 을 먼저 두는 이유**: 하네스를 기존 스키마 위에서 먼저 만들면 하네스 자체가 검증되고,
그다음 위험한 재설계(Phase 2)에 **안전망이 생긴다.** 순서를 뒤집으면 "테스트가 없는 상태에서 145개
쿼리를 다시 쓰는" 일이 된다.

## 1. SQLite 를 채택하지 않는다 — 실측 근거

SQLite 병행 지원은 목표("구현·테스트 용이")에는 맞지만 수단이 틀렸다. 이 코드베이스는 집계·파생값을
SQL 안에서 계산하는 것이 설계 원칙(DTO 서버 단일 소스)이고, 그 SQL 이 PostgreSQL 전용 기능에 깊이 의존한다.

`api/` + `db/` 실측 (2026-09-03):

| 구문 | 횟수 | SQLite 에서 |
|---|---|---|
| `::jsonb` · `jsonb_*()` | 83 | JSON1 함수로 전부 재작성 |
| `AT TIME ZONE` · `::date` · `date_trunc` · `::interval` | 81 | **타임존 함수 없음** — `APP_TZ` 일자 경계를 앱에서 계산 |
| `FILTER (WHERE …)` · `LATERAL` | 42 | LATERAL 없음 |
| `ON CONFLICT DO UPDATE` · `RETURNING` | 58 | 3.35+ 한정 |
| `pg_advisory_xact_lock` · `to_regclass` · `generate_series` · `DISTINCT ON` | 20 | 대응 없음 |
| `.query()` 호출부 | 145 | 전부 두 방언 |

세 가지가 치명적이다.
1. **테스트가 다른 엔진을 검증한다.** SQLite 에서 통과한 대시보드 집계가 PostgreSQL 에서 타임존 경계
   하나로 어긋난다. 회귀를 잡으려는 테스트가, 회귀가 가장 잘 나는 지점에서 눈을 감는다.
2. **추상화 계층이 강제된다.** 145 호출을 두 번 쓰지 않으려면 쿼리 빌더/ORM 이 필요하고, 그 순간
   "SQL 이 단일 소스" 규범이 깨진다. API 6.6k LOC 의 절반이 다시 쓰인다.
3. **영구 세금이다.** 이후 모든 쿼리가 두 방언에서 검증되어야 한다. 1인 개발에서 기능마다 반복된다.

동시성 모델도 다르다 — `ai_jobs` 중복 방지가 advisory lock 에, 워커·세마포어가 커넥션 풀에 의존한다.

## 2. 대안 — 같은 엔진, 두 드라이버 (실측 검증됨)

방언을 늘리지 말고 **실행 방식**만 둘로 둔다. `.env`:

```
DB_DRIVER=pg        # 기본. 실 PostgreSQL (PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD)
DB_DRIVER=pglite    # 개발·테스트. WASM PostgreSQL, 설치 불필요
PGLITE_DATA_DIR=    # 비우면 메모리(테스트마다 새 DB), 경로를 주면 파일 영속
DB_SCHEMA=jina      # 전용 스키마 (Phase 2)
```

[PGlite](https://www.npmjs.com/package/@electric-sql/pglite) 는 PostgreSQL **자체**를 WASM 으로 컴파일한
것이라 SQL 을 한 줄도 바꾸지 않는다. 대체 경계는 `api/lib/pool.js` **한 파일**이고 145개 호출부는 무변경이다.

### 2.1 실측 결과 (`@electric-sql/pglite@0.5.8`, 2026-09-03)

`PGlite.create()` → `SHOW server_version` = **18.3** (진짜 Postgres). 이 프로젝트가 쓰는 구문을 직접 실행:

| 검증 항목 | 결과 |
|---|---|
| `BIGSERIAL` · `TIMESTAMPTZ` · `CHECK(num_nonnulls…)` · 정규식 CHECK(`~`) | OK |
| `ON CONFLICT … DO UPDATE … RETURNING` | OK |
| `jsonb_typeof` · `jsonb_array_length` · `jsonb_each_text`(오답 노트 쿼리) | OK |
| `AT TIME ZONE 'Asia/Seoul'` · `::date` · `date_trunc` · `::interval` | OK |
| `generate_series`(주간 7칸) · `FILTER (WHERE)` · `DISTINCT ON` · `LATERAL` | OK |
| `to_regclass`(테이블 부재 폴백) · 부분 UNIQUE 인덱스 · CTE + 윈도우 함수 · `DO $$` | OK |
| `transaction()` + `pg_advisory_xact_lock(hashtext($1))` | OK |
| `SET statement_timeout` | OK |
| 파일 영속 → 프로세스 재시작 후 재오픈 | OK |

**어댑터가 반드시 처리할 차이 1건 (실측):** `pool.js` 는 `pg.types.setTypeParser(20, Number)`(BIGINT)와
`(1700, Number)`(NUMERIC)로 문자열 반환을 막는다. PGlite 는 BIGINT 는 `number` 로 주지만
**NUMERIC 은 `"2.50"` 문자열로 준다.** 그대로 두면 `pool.js` 주석이 경고한 "프론트 비교·산술이 조용히
깨지는" 상황이 재현된다. PGlite 는 쿼리 옵션으로 파서를 받으므로 어댑터가 항상 주입한다:

```js
await db.query(sql, params, { parsers: { 1700: Number } })   // 실측 확인: 2.5 (number)
```

### 2.2 PGlite 의 한계 — 무엇을 못 잡는가

- **단일 커넥션이다.** `PG_POOL_MAX` 는 의미가 없고 트랜잭션이 직렬화된다. advisory lock 은 동작하지만
  **경합이 없어 동시성 버그를 잡지 못한다.** `ai_jobs` 중복 방지·워커 경합·세마포어는 `DB_DRIVER=pg` 로
  검증해야 한다(기존 `verify-lesson-gen.mjs` 의 역할).
- **버전 스큐.** PGlite 는 PostgreSQL 18 이고 실 서버 버전은 환경마다 다르다. 18 에서 통과한 문법이
  구버전에서 거부될 수 있다 → CI 는 `pglite` 로 빠르게, 릴리스 전 1회는 `pg` 로 전체 회귀(Phase 3).
- **0.x 이다.** 2026-08-26 릴리스, 활발하지만 pre-1.0 이라 API 파괴 변경 가능 → **정확한 버전 고정**.
- **Node 버전 미확인.** 패키지에 `engines` 필드가 없고, 실측은 Node 22 에서 했다. `package.json` 은
  `>=18` 이다 — Node 18 에서 PGlite 와 `node:test` 를 확인하고, 안 되면 `engines` 를 `>=20` 으로 올린다
  (열린 질문 2).

## 3. 스키마 재설계

### 3.1 전용 스키마

새 데이터베이스 + 전용 스키마 `jina`(`DB_SCHEMA`). 얻는 것:

- `db:reset` 이 `DROP SCHEMA jina CASCADE` 한 줄이 된다 → `RESET_TABLES` 22개 수기 목록과
  `FOREIGN_TABLES` self-assert가 **사라진다**. 지금은 테이블을 추가할 때마다 이 목록을 FK 역순으로
  갱신해야 하고, 플랜 11·13 이 반복해서 그 부담을 적고 있었다.
- 최소권한 롤 분리(`db/README` 후속 과제)의 GRANT 범위가 명확해진다.
- 다른 앱 테이블 11개와 물리적으로 분리된다.

쿼리의 `public.` 접두 145곳은 `search_path` 를 스키마로 고정하고 **접두를 제거**한다(어댑터가 두 드라이버
모두에 `SET search_path` 를 건다). 접두를 `jina.` 로 바꾸는 것보다 낫다 — 스키마 이름이 코드에 박히지 않는다.

### 3.2 콘텐츠 카탈로그 통합

```
content_items                         -- 콘텐츠 공통 상위. 가시성·감사·토픽 구성이 전부 여기만 본다
  id, type (lesson|scenario|vocab_set|speaking_set),
  slug UNIQUE, title, description, difficulty,
  status (draft|review|published|archived), visibility (public|private),
  source (seed|ai|curated), created_by, updated_by, created_at, updated_at
  CHECK (status = 'published' OR visibility = 'private')     -- 11 결정 2

lesson_details      (content_id PK → content_items)  kind, subtitle, est_minutes, passage, vocab, faq, position
scenario_details    (content_id PK)                  tag, level, system_prompt, opening_message, objectives
vocab_set_details   (content_id PK)                  words
-- speaking_set_details 는 13 Phase C (플랜 10 실측 통과 후)

lesson_items.content_id            → content_items    (lesson_id 개명)
user_lesson_attempts.content_id    → content_items    (lesson_id 개명)
lesson_drafts.published_content_id → content_items
topic_contents (topic_id, content_id, position)  UNIQUE (topic_id, content_id)
   -- 배타 FK · 부분 UNIQUE 3개 · num_nonnulls CHECK 전부 소멸
content_audit_log.content_id       → content_items    (다형성 아닌 진짜 FK)
topics: status·visibility·updated_by 를 baseline 에 포함
```

이 통합으로 플랜 11 이 예정했던 것들이 **불필요해진다**: `0017_content_status.sql`,
`lessons.published` 정합성 CHECK(컬럼 자체가 없다), 네 테이블에 `status` 개별 추가, 13 의 배타 FK 확장.

**같은 김에 고치는 것 하나 — LC 스크립트 구조화.** 지금 `passage.body` 는 `"W: Do you have…"` 문자열
배열이고, 재생은 정규식으로 화자 라벨을 떼고 `validateLcScript` 도 문자열을 파싱한다. 13 의 에디터가
줄 단위로 편집할 대상이므로 `[{speaker: 'W'|'M', text}]` 로 바꾼다. 영향: `listening.jsx`,
`speaking.service.js`(문장 은행), `validateLcScript`, `lesson_gen` LC 스키마·프롬프트.

**범위에 넣지 않는 것**: `user_lesson_attempts.answers` JSONB 를 문항 단위 행으로 쪼개는 것.
사용자당 수백 건 규모에서 이득이 없다(08 구현자 메모의 판단 유지). 이 플랜의 목표는 성능이 아니라 구조다.

## 4. Phase 플랜

### Phase 1 (2~3일) — 드라이버 어댑터 + 테스트 하네스 (**스키마 무변경**)

이 Phase 만으로 앱 동작은 하나도 바뀌지 않는다. 순수하게 안전망만 만든다.

| 산출물 | 세부 |
|---|---|
| `api/lib/db.js` | `DB_DRIVER` 분기. `query(sql, params)` / `tx(fn)` 두 함수만 노출. pg: 지금 `pool.js` 그대로. pglite: `PGlite` + `parsers:{20:Number,1700:Number}`(§2.1) + `SET search_path`·`SET statement_timeout` |
| `api/lib/pool.js` | `db.js` 재노출로 축소(호출부 145곳 무변경) |
| `api/config.js` | `DB_DRIVER`·`PGLITE_DATA_DIR`·`DB_SCHEMA` 추가. `pg` 일 때만 `PGHOST` 등 `required()` |
| `package.json` | `@electric-sql/pglite` **정확한 버전 고정**, `"test": "node --test tests/"`, `package-lock.json` 을 `.gitignore` 에서 제거(재현 가능한 설치) |
| `tests/helpers/db.mjs` | 메모리 PGlite 에 마이그레이션 적용 + 시드 → 격리된 DB 를 테스트마다 |
| `db/migrate.mjs` · `db/seeds/dev.mjs` | (Phase 1 에서 추가) 드라이버 인식. 러너는 advisory lock 이 세션 단위라 풀이 아니라 전용 커넥션을 계속 쓴다. 시드는 `pool.connect()` 로 BEGIN/COMMIT 구간을 한 커넥션에 묶는다 |
| `api/lib/pglite-lock.js` | (Phase 1 에서 추가) 파일 DB 의 PID 잠금. 두 프로세스가 같은 디렉터리를 열면 서로의 쓰기를 못 본다(실측) — 두 번째 프로세스를 거부한다 |
| `tests/` 첫 묶음 | DB 가 필요하되 서버·AI 가 불필요한 순수 서비스 로직 — `srs.js` 예측, `dashboard.service` 스트릭 산식, `lesson.service` 채점·멱등, `progress.service` 집계, `pronunciation-normalize`, `speaking.service` 문장 판별 |

완료 판정: `npm test` 가 **DB·서버·AI provider 없이** 통과. 같은 테스트가 `DB_DRIVER=pg` 로도 통과
(두 드라이버 동등성). 기존 `e2e-*`·`verify-*` 전부 무회귀.

### Phase 2 (4~5일) — baseline + 카탈로그 통합 + 시드 데이터화 + 서비스 이관

**Phase 1 과 달리 중간 상태가 없다.** 스키마를 바꾸는 순간 앱이 깨지므로 이 Phase 는 하나의 PR 로 간다.

## 6. 구현자 메모

- `db.js` 는 `query`/`tx` 두 함수만 노출한다. `pool.on('error')`(원격 유휴 커넥션 단절로 서버가 죽는 것을
  막는 기존 방어)는 pg 드라이버 쪽에 그대로 유지 — pglite 에는 해당 사항이 없다.
- 어댑터에서 `SET statement_timeout` 은 세션 단위다. 지금은 pg 연결 문자열의 `options` 로 넣고 있는데,
  pglite 는 그 경로가 없으므로 두 드라이버 모두 부팅 시 세션 설정으로 통일한다.
- `to_regclass` 폴백(01/02 테이블 부재 DB 에서도 대시보드 200)은 baseline 이후 무의미해진다 — 한 파일이
  전부를 만든다. 제거 여부는 Phase 2 에서 판단(제거하면 `dashboard.service` 가 눈에 띄게 단순해진다).
  > **판단 (2026-09-04): 이번에는 테이블 이름만 고치고 남긴다.** 제거는 `dashboard`·`progress` 두 파일의
  > 분기 25곳을 건드리는데, Phase 2 의 유일한 성공 기준은 DTO 무회귀이고 제거의 이득은 가독성뿐이다.
  > 회귀 위험을 이 PR 에 얹지 않고, 별도의 작은 정리 커밋으로 분리한다.
- 시드 JSON 은 스키마를 갖는다(`db/content/README.md`). 관리자 저작(13)이 들어오면 이 포맷이 export
  대상이 되므로 처음부터 DTO 와 가깝게 만든다.
- 마이그레이션 파일을 지우는 것은 이 프로젝트 규범("적용된 파일 수정 금지")의 **예외**다. 전제(드롭 가능)가
  근거이고, 같은 예외를 다시 쓰려면 이 문서를 갱신해야 한다.
- PGlite 데이터 디렉터리(`PGLITE_DATA_DIR`)를 `.gitignore` 에 추가한다.

## 7. 열린 질문

1. **새 데이터베이스·스키마 이름** — DB `jina`, 스키마 `jina` 를 기본으로 제안. 다른 앱과 같은 인스턴스를
   계속 쓸지(스키마 분리만) 별도 인스턴스로 갈지는 환경 사정.
2. **Node 최소 버전** — PGlite 와 `node:test` 를 Node 18 에서 확인. 안 되면 `engines` 를 `>=20` 으로
   올린다(실측 환경은 Node 22 였다).
   > **결정 (2026-09-04): `>=20.6`.** 측정이 아니라 요구사항에서 나온 값이다 — `npm test` 가
   > `node --import` 로 테스트 프리로드(`tests/setup.mjs`)를 걸고, 그 플래그가 Node 20.6 에서 들어왔다.
   > Node 18 은 2025-04 에 EOL 이라 하한을 되돌릴 이유도 없다. CI 는 Node 20 으로 돌린다.
3. **`DB_DRIVER=pglite` 를 개발 기본값으로 둘지** — DB 설치 없이 `npm run dev` 가 뜨는 것은 매력적이지만,
   개발자가 실 PostgreSQL 과 다른 환경에서 계속 작업하게 된다. 테스트 전용으로 두는 편이 안전해 보인다.
   > **결정 (2026-09-03)**: 저장소 기본값은 `pg` 로 유지하고(`.env.example`), PostgreSQL 이 없는 환경에서만
   > 각자의 `.env` 로 `pglite` 를 쓴다. 그 환경에서 감수하는 것: 단일 커넥션이라 `PG_POOL_MAX` 가 무의미하고
   > 동시성 버그가 드러나지 않으며, `statement_timeout` 이 동작하지 않고, PG 18 로 개발해 실제 서버 버전과
   > 어긋날 수 있다. 그래서 릴리스 전 회귀는 `DB_DRIVER=pg` 로 한 번 더 돌린다(Phase 3).
4. **`lesson_items`·`user_lesson_attempts` 의 컬럼명** — `lesson_id` → `content_id` 개명은 의미가 맞지만
   "레슨 시도" 라는 도메인 용어와 멀어진다. `content_id` 로 통일 vs `lesson_id` 유지(FK 대상만 교체).
5. **`type` 별 detail 테이블 vs `content_items.detail JSONB`** — detail 3~4개 테이블이 조인을 늘린다.
   JSONB 한 컬럼이면 조인이 없지만 CHECK 로 지키던 구조 검증을 잃는다. 전자를 제안(현재 스키마가 이미
   `passage`·`options` 를 JSONB 로 두고 나머지는 컬럼으로 둔 절충과 같은 결).
