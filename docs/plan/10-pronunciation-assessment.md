# 10 — 발음 평가: 방식 비교와 도입 플랜 (2026-09-01)

플랜 08 Phase C 가 후속으로 미뤄둔 "발음 평가 API" 선택과 도입 플랜.
현재 스피킹 화면은 **브라우저 STT + 단어 매칭**으로 동작하고, 화면에 나오는 수치는
'발음 점수'가 아니라 **'받아쓰기 일치율'** 이다(의도적 표현 — §1 참조).

> 이 문서는 두 갈래로 쓰였다: **§1~§4 = 방식 비교와 선택 기준**, **§5~§8 = 실제 도입 플랜**.
> 무엇을 살지 정하는 사람은 앞을, 붙이는 사람은 뒤를 보면 된다.

## 0. 결론 먼저

| 단계 | 선택 | 상태 |
|---|---|---|
| 지금(무료·프로토타입) | **브라우저 STT 유지** | 완료 — '받아쓰기 일치율'이라는 이름을 지키고, 발음 점수가 아님을 화면이 명시한다 |
| 다음 | **자체 호스팅(OpenPronounce)으로 발음 점수 도입** | 사이드카 설치 스크립트 준비 완료([`lib/pronounce`](../../lib/pronounce/README.md)) · **실측 검증 대기** |
| 대안 | 상용 API(Speechace / Azure) | 로컬 추론이 느리거나 점수 캘리브레이션이 부족할 때 |

**핵심**: 세 방식은 정확도 차이가 아니라 **측정 대상 자체가 다르다.**
브라우저 STT는 "무슨 단어로 들렸나", Speechace/GOP는 "그 소리가 목표 음소에 얼마나 가까운가"를 잰다.

## 1. 지금 구현이 실제로 재는 것

`src/screens/speaking.jsx` 의 `matchWords()` — 목표 문장과 인식 결과를 LCS 로 정렬해
단어별로 일치/치환/누락 3색을 칠하고 일치율 %를 낸다.

이건 **발음 점수가 아니다.** 브라우저 STT(내부적으로 강한 언어모델 보정)가
`vendor` 를 어색하게 읽어도 문맥으로 `vendor` 라고 적어주면 100% 가 나온다.
반대로 발음이 멀쩡해도 잡음·마이크 문제로 단어가 통째로 날아가면 0점이 된다.

→ 그래서 UI 문구를 "받아쓰기 일치율"로 두고, 점수보다 **교정 힌트**를 크게 배치했으며,
하단에 "이 수치는 발음 점수가 아니다"를 명시한다(`speaking-disclaimer`).
이 표현은 실제 발음 평가를 붙이기 전까지 바꾸지 않는다.

## 2. 세 방식은 측정 대상이 다르다

| | 받아쓰기(ASR) — 브라우저 STT · Whisper | 발음 평가 |
|---|---|---|
| 답하는 질문 | "이 사람이 **무엇을** 말했나" | "이 사람이 목표 문장을 **얼마나 정확히** 발음했나" |
| 목표 문장 | 모름 (그래서 언어모델 사전확률로 추측·보정) | **알고 있음** → 음소 단위 강제 정렬(forced alignment) |
| 틀린 발음 | 문맥상 그럴듯한 단어로 **고쳐서** 받아 적음 → 오류가 사라진다 | 음소별 점수로 **드러난다** |
| 산출 | 텍스트 | 정확도·유창성·완성도·운율 + 단어·음소별 점수 |

즉 **Whisper 로 바꿔도** "vendor 를 bender 로 읽었다"는 여전히 `vendor` 로 복원되고 비용만 는다.
받아쓰기 일치율은 *문장을 빠뜨리지 않고 읽었는지* 를 보는 지표로는 쓸모가 있어 폴백으로 남긴다.

| 항목 | 브라우저 STT (현재) | 상용 API (Speechace/Azure) | 자체 GOP |
|---|---|---|---|
| **측정 단위** | 단어(전사 일치 여부) | 음소·음절·단어·문장 | 음소(설계하기 나름) |
| **진단력** | "다른 단어로 들림"까지 | "θ를 s로 발음", 강세·유창성 | 음소 이탈도(라벨링 품질에 좌우) |
| **점수 신뢰도** | 캘리브레이션 없음 | 사람 채점 기준으로 튜닝됨 | **직접 캘리브레이션해야 함** |
| **비용** | 0 | 요청 단위 과금 | 인스턴스 + 개발·튜닝 공수 |
| **지연** | 즉시(스트리밍, 중간 결과) | 녹음 종료 후 왕복(수백 ms~수 초) | 모델·하드웨어에 따라 큼 |
| **브라우저 커버리지** | **Chrome/Edge/Safari만.** Firefox 기본 미지원 | 전부(오디오만 올리면 됨) | 전부 |
| **음성 전송** | Chrome/Edge → Google, Safari → Apple 서버 | 벤더 서버 | 자체 서버(외부 전송 0) |
| **오프라인/온프레미스** | 불가 | 불가 | 가능 |
| **구현 공수** | 완료 | 며칠(녹음 업로드 + 응답 매핑) | 며칠~수 주(§3.3) |
| **HANDOFF §7 `word_scores` 충족** | ✗ | ○ (거의 그대로) | ○ (직접 만들어야) |

## 3. 각 방식의 실체

### 3.1 브라우저 STT (Web Speech `SpeechRecognition`)

- **장점**: 비용 0, 설치 0, 중간 결과가 실시간으로 나와 UX 가 즉각적이다.
- **함정 1 — 커버리지**: Firefox 는 기본 미지원. 데스크탑 우선 정책(`mobile:false`)과 겹쳐
  실사용 브라우저를 좁힌다. 지금 화면은 미지원/권한 거부를 구분해 안내하고 있다.
- **함정 2 — 언어모델 보정**: 정확한 발음을 요구하는 평가에는 구조적으로 부적합하다.
  "알아들었다"와 "잘 발음했다"가 다르다.
- **함정 3 — 프라이버시**: 무료지만 음성은 브라우저 벤더 서버로 나간다. Chrome 139 의
  on-device Web Speech 는 이걸 개선하지만 여전히 받아쓰기다.
- **`confidence` 를 점수로 쓰면 안 된다**: 스펙에 발음 평가는 없고 `SpeechRecognitionAlternative.confidence`
  (0~1)뿐인데, 이는 인식 신뢰도이고 무음·저품질 오디오에서 오히려 높게 튄다.
- 무료로 더 짜낼 수 있는 것: Web Audio API 로 발화 속도·침묵 구간·피치/에너지 곡선 →
  *유창성·운율* 근사는 0원으로 가능하다(정확도 축만 비어 있다).

### 3.2 상용 발음 평가 API

| 후보 | 가입 마찰 | 무료 조건 | 산출 |
|---|---|---|---|
| **Speechace** | **없음** — 가입 없이 기본 키로 시작 | **하루 5회** | 음소·음절·단어·문장 + CEFR/IELTS 환산 |
| **Azure Pronunciation Assessment** | 셀프서비스(구독 필요) | 무료 F0 티어(한도는 포털 확인) | 정확도·유창성·완성도·운율 + 음소별 |
| SpeechSuper | appKey/secretKey 를 **직접 문의**해야 발급 | 프리미엄 | 8개 언어, 음소~문장 |
| ELSA | **영업 문의 전용**, 개발자 가격 비공개(팀 플랜 $18.2/user/월) | 없음 | 음소·강세·억양 + IELTS/TOEFL 예측 |

- Speechace·Azure 는 HANDOFF §7 이 이미 정의해둔 `word_scores: [{word, score}]` + `wordColor()`
  색상 매핑에 거의 그대로 대응된다 — 화면을 새로 설계할 필요가 없다.
- **가격은 공개 표준가가 아니라 계약 조건에 따르므로 직접 확인할 것.** 이 문서에 단가를 적어두지 않는다
  (추정치를 사실처럼 굳히지 않기 위해).
- SpeechSuper·ELSA 는 개인 프로젝트가 키를 얻는 것 자체가 마찰이다. **PoC 에는 Speechace 의
  "가입 없이 하루 5회"가 가장 싸다** — 응답 계약과 화면을 확정하는 데 5회면 충분하다.

### 3.3 자체 GOP 구현

원리(직접 만들 경우):
1. **목표 음소열 생성** — 문장 → G2P(CMUdict / espeak-ng)로 기대 음소 시퀀스.
2. **강제 정렬(forced alignment)** — 음성과 목표 음소를 시간축에 맞춘다(MFA, Kaldi, wav2vec2 CTC).
3. **GOP 점수** — 각 구간에서 *목표 음소의 사후확률* vs *최고 확률 음소* 를 비교한다.
4. **캘리브레이션** — GOP 원값은 사람 점수와 스케일이 다르다. 사람 채점 데이터로 보정해야
   "58점"이 의미를 가진다. 공개 데이터셋 **speechocean762**(L2 영어, 음소·단어·문장 사람 점수)가
   사실상 표준 출발점이다.

**진짜 비용은 GPU 가 아니라 4번이다.** 1~3번은 오픈 모델로 며칠이면 붙지만, 캘리브레이션 없이
내보내면 "왜 이 점수인지 설명 못 하는 숫자"가 되고 학습자 신뢰를 잃는다.

**다만 1~3번은 직접 만들 필요가 없다** — [OpenPronounce](https://github.com/Halleck45/OpenPronounce)
(MIT, Wav2Vec2 + DTW, 2026-08 기준 활발)가 스스로를 "Azure Pronunciation Assessment 의 자체 호스팅
대안"으로 규정하고 이미 그 일을 한다.

```
$ openpronounce recording.wav "Hello, how are you?"
Score: 59.0/100   Transcription: HELL NO WHO ARE YOU
  - hello: expected /həloʊ/, heard /hɛlnoʊ/ (confidence 89%)
```

- **CPU 로 동작**하고 HTTP 서버로 띄울 수 있다. 비용 0 · 호출 제한 없음 · **학습자 음성이 외부로 나가지
  않는다**(학습자가 아이라면 이 항목이 크다).
- 대가: Wav2Vec2 체크포인트 2개(~1.2GB 씩) 최초 다운로드, CPU 추론 지연, 그리고 **46 stars 규모라
  4번(캘리브레이션 검증)은 여전히 우리 몫**이다 — 위 경고가 그대로 적용된다.
- 설치·기동은 [`lib/pronounce`](../../lib/pronounce/README.md) 에 스크립트 2종(Docker · 네이티브 venv)으로 준비돼 있다.

## 4. 이 앱 기준 권고

1. **화면 문구는 지금 상태를 유지한다.** 무저장 연습 모드에 브라우저 STT + '받아쓰기 일치율'이면
   충분하고, 실제 발음 점수를 붙이기 전까지 두 이름을 섞지 않는다.
2. **백엔드를 하나로 못 박지 않는다.** `pronunciation.service.js` 가 어댑터를 고르고 응답을 한 모양으로
   정규화한다(`AI_PROVIDER` 가 CLI 프로바이더를 고르는 것과 같은 패턴). 어댑터 2개로 시작:
   `openpronounce`(로컬) · `speechace`(PoC·대안).
3. **먼저 자체 호스팅을 검증한다.** 이 앱은 이미 Ollama 사이드카를 운영 중이라 같은 패턴 하나를
   더 붙이는 셈이고, 요청당 과금 0 · 음성 외부 전송 0 을 얻는다. **단 §3.3 의 캘리브레이션 경고가
   해소되지 않으면 상용 API 로 간다** — 그 판단 기준이 Phase 1 의 검증 항목이다.
4. **어느 쪽을 붙이든 '일치율'과 '발음 점수'는 화면에서 구분해 표시한다.**
   같은 숫자처럼 보이면 사용자가 폴백 모드의 일치율을 발음 점수로 오해한다.

## 5. 설계 결정 (도입)

1. **오디오는 서버를 경유한다** — 키를 클라이언트에 노출하지 않고, 로컬 어댑터에서는 어차피 서버가
   사이드카를 부른다. `MediaRecorder`(HANDOFF §7 패턴) → `POST /api/speaking/assess` → 어댑터 → 점수만 응답.
2. **오디오는 저장하지 않는다** — 평가 후 즉시 폐기, 점수·음소 결과만 DB 에(§8-2 에서 재결정 가능).
3. **백엔드가 없으면 v1 으로 자동 폴백** — 미설정이 정상 상태다. 화면은 현재 모드를 배지로 밝힌다
   ("발음 평가" / "받아쓰기 연습"). 503 을 던지지 않는다.
4. **통계 연결** — `dashboard.service.js:355` 의 `{ key: 'speaking', pct: null, '데이터 없음' }` 자리를
   발음 점수 30일 평균이 채운다. 플랜 08 §2.5 가 Listening 을 채운 것과 같은 방식(소스만 추가).
5. **v1 매칭 로직은 삭제하지 않는다** — `window.jinaMatchWords` 는 폴백 모드와 회귀 테스트가 함께 쓴다.

## 6. Phase 플랜

### Phase 1 — 서버 평가 경로 (어댑터 2종)

| 산출물 | 세부 |
|---|---|
| `POST /api/speaking/assess` | multipart(오디오) + `reference_text`. 응답 `{backend, pron_score, accuracy, fluency, completeness, prosody, words:[{word, score, expected_ipa, heard_ipa, phonemes:[{p, score}]}]}` |
| `api/services/pronunciation.service.js` | 어댑터 선택 + 응답 정규화. 백엔드 미설정이면 `{available:false}` → 라우트는 200 으로 폴백 신호 |
| `openpronounce` 어댑터 | [`lib/pronounce`](../../lib/pronounce/README.md) 사이드카에 프록시 — **설치 스크립트 2종 작성 완료**. `.env` `PRONUNCIATION_URL=http://localhost:8000` |
| `speechace` 어댑터 | 가입 없이 기본 키로 계약 확정용. 하루 5회 한도를 코드가 알고 429 를 폴백으로 처리 |
| 검증 | `verify-pronunciation.mjs`: 고정 wav 픽스처(잘 읽은 것 1 · 틀리게 읽은 것 1)로 실호출 → **틀린 쪽 점수가 실제로 낮게 나오는지**까지 단정(§3.3 캘리브레이션 경고에 대한 최소 방어). 백엔드 없으면 스킵(실패 아님) |

### Phase 2 — 화면

| 산출물 | 세부 |
|---|---|
| 녹음 | `MediaRecorder` 캡처(SpeechRecognition 은 오디오를 넘겨주지 않아 별도 캡처 필요) |
| 결과 렌더 | v1 3색 → **점수 그라데이션** + 단어 클릭 시 음소별 상세(expected /həloʊ/ → heard /hɛlnoʊ/). 임계값은 HANDOFF §7 그대로(≥85 success / ≥65 warning / 미만 error) |
| 모드 배지 | 발음 평가 / 받아쓰기 폴백 중 무엇으로 채점됐는지 표시. v1 disclaimer 는 폴백 모드에서만 |
| 검증 | 기존 STT 모킹 회귀 유지 + assess 응답 모킹으로 음소 렌더 단정 |

### Phase 3 — 저장 · 통계

| 산출물 | 세부 |
|---|---|
| 마이그레이션 | `speaking_attempts`(user_id, sentence_text, source, backend, pron_score, accuracy, fluency, completeness, prosody, words jsonb, created_at), 인덱스 `(user_id, created_at desc)` |

## 7. 구현자 메모

- v1 채점 중복 버그(플랜 08 Phase C)와 같은 함정: `MediaRecorder` 도 `stop()` 이 비동기이고 마지막
  `dataavailable` 가 늦게 온다. 업로드는 `onstop` 이후 한 번만.
- 오디오 포맷: 브라우저는 `audio/webm;codecs=opus`. OpenPronounce 의 `load_audio` 가 librosa 로 못 읽는
  포맷은 ffmpeg 로 디코딩해 16kHz mono 로 리샘플하므로 **webm 을 그대로 넘겨도 된다**(소스 확인).
  Speechace 는 허용 포맷을 별도 확인할 것.
- **PyPI 휠에는 웹앱(`server.py`)이 없다** — 라이브러리와 CLI 만 들어 있어 저장소 클론 없이는
  `uvicorn server:app` 이 동작하지 않는다. 그래서 `lib/pronounce/server.py` 로 필요한 두 엔드포인트만 감쌌다.
- **TTS 기본값이 gTTS 라 온라인이다** — `compare_audio_with_text` 는 목표 문장을 TTS 로 합성해 DTW 비교를
  하고, 기본 백엔드는 그 문장 텍스트를 Google 로 보낸다. `OPENPRONOUNCE_TTS=piper` +
  `openpronounce[tts-piper]` 로 완전 오프라인이 된다(설치 스크립트·Dockerfile 에 반영됨).
  어느 쪽이든 학습자 음성은 나가지 않는다.
- **Windows 의 phonemizer 는 `PHONEMIZER_ESPEAK_LIBRARY` 를 요구한다** — espeak-ng 를 설치해도 DLL 경로를
  환경변수로 주지 않으면 못 찾는다. `install-python.ps1` 이 경로를 찾아 설정한다(Docker 방식은 무관).
- 사이드카가 꺼져 있는 것은 버그가 아니다 — 어댑터는 v1 폴백으로 내려가야 한다.
  (Ollama 미기동으로 E2E 가 대량 503 실패한 전례가 있다.)
- `speech.jsx` 의 `useJinaSpeechRecognition` 은 그대로 둔다 — 폴백 모드와 회화 탭 받아쓰기가 계속 쓴다.
- 모바일은 `mobile:false` 유지(플랜 08 §2.6).

## 8. HANDOFF 문서와의 불일치 (이 문서로 정정)

- §6 비용표는 음성 인식을 **Whisper** 로 잡아뒀는데, §7 은 **단어별 발음 점수**를 전제한다.
  Whisper 는 전사(ASR) 모델이라 `word_scores` 를 만들지 못한다 — 악센트에 강건하도록 설계돼 있어
  오히려 발음 오류를 지운다.
- 정정: **Whisper 는 리스닝 받아쓰기·자유 회화 서버 STT 용도**로 남기고, 발음 평가는 별도 항목
  (자체 GOP 또는 Speechace/Azure)으로 잡는다. (HANDOFF §6·§7 에 반영 완료)

## 9. 열린 질문

1. **자체 호스팅으로 갈 것인가** — 사이드카(2.4GB 모델 + 상시 기동)를 받아들일지가 갈림길이다.
   설치 스크립트는 준비됐고 **실측 검증이 다음 착수점**이다.
2. 평가 이력을 저장할지(현재 v1 무저장). 저장하면 점수 추이·약점 음소 집계가 가능해지지만
   음성 원본 보관 여부·기간을 개인정보 처리방침에 명시해야 한다(§5.2 는 폐기가 기본).
3. 로컬 추론 지연이 학습 흐름을 끊을 정도라면(문장당 수 초) 어떻게 할지 — 상용 API 전환 또는 GPU.
4. 무료 티어에 발음 점수를 일부라도 줄지 — 준다면 일 N회 제한이 필요하다.
5. 한국인 학습자 특화 약점(θ/ð, r/l, f/p, 최종 자음군)을 별도 리포트로 뽑을지 —
   음소 단위 점수가 있어야 가능하므로 Phase 3 이후.
6. TOEIC Speaking 공식 문형(Q1~Q11) 확장은 이 플랜 범위 밖 — 읽기(Q1~2) 유지.
